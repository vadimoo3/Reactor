# Reactor Lab

Одна локальная программа для поиска, улучшения и проверки раскладок Reactor Incremental Build 24. Название программы и существующие режимы сохранены.

## Как пользоваться

Запустите `ReactorLab.exe`. Выберите топливо, разрешённые размеры клеток, бюджет, допустимые покупки улучшений и время. Галочка «Точное количество стержней» задаёт число топливных клеток: Quad считается одной клеткой. Если разрешён один размер, все клетки будут именно этого размера. Если разрешены несколько, возможны смешанные составы.

Все четыре режима используют один движок и одну популяцию кандидатов:

- **Блоки** — приоритет модулей и структур охлаждения.
- **Полный рандом** — приоритет случайных полей и свободных мутаций.
- **Улучшение** — старт от выбранной схемы с повторной проверкой исходного результата.
- **Блоками** — старт от выбранной схемы с приоритетом повторяемых фрагментов.

Приоритет не отключает остальные способы поиска. Схемы библиотеки поступают в общий стартовый пул. Геометрии ранней модели можно использовать как исходные топологии; их старые мощности и улучшения не переносятся. Число топлива ограничивают бюджет, размер поля и явный запрос пользователя; прежних пределов 6–8 клеток в общем поиске нет. Движок поддерживает прямоугольные поля от 3×3 до 60×60; это программный диапазон, а не утверждение о доступном в игре размере поля.

Результаты отображаются в списке схем. Для лучших вариантов сохраняется класс проверки: защищённая схема или схема без аварийного запаса. По завершении выбирается лучший по чистой выработке вариант, включая схему без аварийного запаса; класс проверки указан явно. Стрелки переключают финалистов. Штатная работа с регулярной ручной заменой Protium не означает автоматическую заправку.

## Единый поиск

`src/engine/anneal.cpp` содержит общий поиск вместо последовательного запуска изолированных генераторов. В нём работают 12 операторов:

1. Случайное поле, включая случайные веса компонентов.
2. Пять исходных типов модулей с произвольным расположением.
3. Контуры с Exchanger.
4. Чередующиеся структуры Exchanger/Vent/Outlet/Plating.
5. Мозаики соседнего топлива, Reflector, Coolant и Inlet.
6. Топливные группы и контуры рециркуляции Outlet/Coolant/Inlet.
7. Свободные замены и перестановки клеток с отжигом.
8. Добавление и замена модулей внутри существующей схемы.
9. Скрещивание прямоугольных участков разных кандидатов.
10. Копирование фрагментов и повторяемые узоры.
11. Изменение состава и размещения топлива в разрешённых пределах.
12. Восстановление охлаждения, подвода Inlet и теплоёмкости Vent после мутаций.

Все операторы используют общую популяцию с группами по составу топлива. Удачные поля и их фрагменты доступны другим операторам сразу. Частоты операторов адаптируются по результатам; часть попыток всегда остаётся для разведки. В популяции остаются и промежуточные схемы со штрафами за перегрев и цену, чтобы поиск мог выйти из неудачной геометрии. В итог попадают только проверенные варианты.

Стоимость, тепло, импульсы соседнего топлива, Reflector, усиление Vent от Capacitor, продажи и расходы на заправку считаются для каждого кандидата. Быстрая оценка учитывает также контуры рециркуляции Forceful Fission. Финальная чистая выработка измеряется динамически: минимум продаж последних 1000 тиков по шести порядкам обработки, минус цена топлива за его ресурс; затем применяется коэффициент Chrono. Это установившаяся метрика при регулярной заправке, а не средняя прибыль первого запуска с холодного корпуса.

Дорогие проверки выполняются параллельно, результаты применяются в фиксированном порядке. Число рабочих потоков ограничено половиной логических процессоров. Повторные успешные тепловые проверки переиспользуются при изменении только Chrono. В симуляторе предварительно вычисляются источники тепла и списки связей, вместо повторного разбора всей сетки на каждом тике.

Исходники прежних алгоритмов в `src/engine/algorithms/` сохранены для совместимости и диагностики. Основной интерфейс больше не запускает их отдельными этапами. Общий поиск остаётся эвристическим: сохранение приёмов построения не означает побитового совпадения прежних генераторов и не доказывает глобальный максимум.

## Единая проверка

Автопроверка интерфейса и отбор поиска используют общий симулятор. Проверяются 30 сочетаний: шесть порядков обработки × штатный режим, отключение Outlet, отключение Vent, отложенная замена топлива и полное выгорание. Длительность не меньше трёх ресурсов топлива; интерфейсная диагностическая проверка по умолчанию идёт 100000 тиков, а поиск использует заданные `simSteps`, увеличенные до необходимого минимума.

В каждом прогоне проверяются корпус и отдельные Exchanger, Vent, Coolant и Capacitor, включая наиболее нагруженный Vent. Защищённый кандидат проходит все сценарии. Кандидат без аварийного запаса обязан пройти штатную работу, замену и выгорание во всех шести порядках. Улучшения, запрещённые пользователем, в результат не добавляются.

Это собственная модель проекта, а не исходный игровой движок. Текущий save не импортируется автоматически в параметры модели; профиль приложения и исторический профиль регрессионных проверок необходимо различать. Бонус накопленных выгораний Protium должен быть отражён в параметрах профиля перед расчётом актуальной сборки.

## Воспроизводимость и локальная работа

`tools/run-engine.ps1 -Tool an -Overrides @{anLibrary='E:\Desktop\Reactor\results\profit'; anSeed='20261027'; anAttempts='50000'; anMinF='6'; anMaxF='6'; anA1='1'; anA2='0'; anA4='0'}` запускает движок без браузера. Без файла параметров скрипт использует исторические значения движка, а не текущий save или ini. `-ParameterFile` принимает файл `ключ=значение`. `-Tool ev` пересчитывает схему из `plFile`, `-Tool pl` проверяет её.

`anAttempts > 0` задаёт воспроизводимое число попыток. При одинаковых параметрах, seed, входных файлах и сборке результат воспроизводится. `anAttempts=0` ограничивает поиск временем; число попыток зависит от скорости компьютера. `anLibrary` задаёт стартовую библиотеку, `anStart` — выбранную схему, `anPopulation` — размер популяции, `anVerify` — предел полного отбора, `anStrategy` — приоритет существующего режима, `anOutFile` — итоговый файл.

В `results/<режим>/runs/<дата>/` сохраняются параметры этапа, журнал, входные схемы, кандидаты, `stats.txt` и `operators.tsv`. Попытки, уникальные поля, варианты улучшений и полные проверки считаются отдельно. Промежуточные файлы скрыты из списка схем. Скрипт запуска дополнительно сохраняет SHA256 движка и код завершения в `runs/`.

## Проверка и сборка

`python tools/test-search.py <абсолютный путь к ReactorEngine.exe>` проверяет старого победителя, все операторы, повторяемость seed, точное топливо на другом размере поля, запрет лишних улучшений и отказ при недостаточном бюджете. Небольшие искусственные профили в тестах проверяют ограничения программы, а не баланс игры.

`ReactorLab.exe --selftest <папка>` запускает проверку интерфейса на копии `results`, `icons` и `ReactorLab.ini`. Отчёт — `selftest-report.txt`, снимки — PNG. Для самопроверки движок распаковывается внутри этой папки.

`src/build.bat` собирает `ReactorLab.exe` с помощью Visual Studio Build Tools. Не следует собирать прямо поверх работающего exe: сначала проверить сборку в рабочем каталоге, затем закрыть приложение и заменить файл под тем же постоянным именем.

## Историческая регрессия

На профиле 19.4504787631017 Qa схема `results/profit/final.txt` даёт 26.0280125472 T/тик продаж, 21.0280125472 T/тик чистыми и стоит 19.142210158 Qa. Общий поиск сохраняет этот результат. Схема проходит штатную работу, отложенную замену и выгорание; отключения Vent/Outlet не выдерживает.

Это контроль старого профиля, а не рекомендация для актуального сохранения с другим бюджетом и уровнями. Точный протокол конкретного поиска хранится рядом с результатами.
